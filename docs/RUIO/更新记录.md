# RUIO-S3CAM-4G 双麦克风 (2MIC + AEC) 适配更新记录

> 适用板子：`vibratalkie`
> 硬件：ESP32-S3R8 + ES8311 (DAC) + ES7210 (ADC) + 双 MEMS 麦克风 ZTS6216
> 更新日期：2026-03-18

---

## 一、目标

将原本单麦克风 + AEC 参考（1M+1R = 2 通道）的音频配置，升级为 **双麦克风 + AEC 参考（2M+1R = 3 通道）**，使两个物理麦克风同时参与收音，提升拾音覆盖范围。

## 三、问题排查与修复过程

### 问题 1：`ESP_FAIL` 崩溃

**现象**：`esp_codec_dev_read()` 返回 `ESP_FAIL`

**原因**：`EnableInput()` 中 `.channel` 被设为 `input_channels_`（=3），但 ES7210 工作在 4 通道 TDM 模式，硬件要求 `.channel = 4`。

**修复**：
```cpp
// box_audio_codec.cc - EnableInput()
esp_codec_dev_sample_info_t fs = {
    .channel = 4,  // 固定为4（ES7210 TDM硬件要求）
    .channel_mask = 0,  // 通过 mask 选择实际通道
};
for (int channel = 0; channel < input_channels_; ++channel) {
    fs.channel_mask |= ESP_CODEC_DEV_MAKE_CHANNEL_MASK(channel);
}
// channel_mask = 0x07 → 选择通道 0,1,2（MIC1,MIC2,REF）
```

---

### 问题 2：MIC2 不收音 — AFE 单麦模式回退

**现象**：日志显示 AFE 内部回退为单麦：
```
W AFE_CONFIG: For single microphone channel, SE is deactivated.
I AFE: AFE Version: (1MIC_V250121)
I AFE: Input PCM Config: total 3 channels(1 microphone, 1 playback)
```

**原因**：`esp-sr` 的 `AFE_TYPE_VC` 不支持双麦 BSS，`se_init` 被内部覆盖为 `false`，回退为单麦模式，只使用通道 0。

**修复**（`afe_audio_processor.cc` + `afe_wake_word.cc`）：
```cpp
afe_config->se_init = (codec_->input_channels() - ref_num) > 1;
afe_config->fixed_first_channel = false;
```

> 注意：即使设了 `se_init=true`，`AFE_TYPE_VC` 仍会回退为单麦模式。
> 因此真正的解决方案是在 codec 层做软件混音（见问题 3）。

---

### 问题 3：自身打断 + MIC2 仍然无声 — ES7210 通道映射错位

**现象**：播放时说话会被自身回声打断，且只插 MIC2 仍然收不到声音。

**根因**：**ES7210 硬件接线约定**中，AEC 参考信号（ES8311 DAC 回环）始终接在 **MIC2 引脚 = TDM Slot 1**：

| TDM Slot | ES7210 引脚 | 实际信号 |
|----------|-------------|----------|
| Slot 0 | MIC1 | 麦克风 1 |
| Slot 1 | MIC2 | **AEC 参考 (REF)** |
| Slot 2 | MIC3 | 麦克风 2 |

代码原本假设通道顺序是 `[MIC1, MIC2, REF]`（"MMR"），但实际硬件顺序是 `[MIC1, REF, MIC2]`（"MRM"）。

- **自身打断**：混音将 ch0(MIC1) + ch1(**扬声器回送**) 叠加 → AEC 拿到的参考数据不对 → 无法消除回声
- **MIC2 无声**：物理 MIC2 在 ch2，但被当成 REF 通道

**修复**（`box_audio_codec.cc - Read()`）：

```cpp
// 步骤1：通道重排 — 把 slot1 的 REF 移到最后
if (input_reference_ && microphone_channels_ >= 2) {
    for (每帧) {
        int16_t ref_val = f[1];          // 保存 REF
        f[1] = f[2];                      // MIC2 前移
        f[2] = ref_val;                   // REF 放末尾
    }
    // [MIC1, REF, MIC2] → [MIC1, MIC2, REF]
}

// 步骤2：混音 — 把所有 MIC 叠加到 ch0
if (microphone_channels_ >= 2) {
    for (每帧) {
        f[0] = saturate(f[0] + f[1]);    // MIC1 + MIC2
        f[1] = 0;                         // 清空
        // f[2] = REF 不动
    }
    // [MIC1, MIC2, REF] → [MIC1+MIC2, 0, REF]
}
```

## 四、ES7210 通道映射原理

ES7210 是 4 通道 ADC，TDM 模式下 **MIC 引脚编号直接对应 TDM 时隙编号**：

```
ES7210 物理引脚    →  TDM Slot  →  实际信号
──────────────────────────────────────────────
MIC1P/MIC1N       →  Slot 0    →  麦克风 1
MIC2P/MIC2N       →  Slot 1    →  AEC 参考（DAC 回环）
MIC3P/MIC3N       →  Slot 2    →  麦克风 2
MIC4P/MIC4N       →  Slot 3    →  （未使用）
```

**所有 ES8311+ES7210 的板子（esp-box / esp-box-3 / 各种 waveshare 等），AEC 参考信号都接在 MIC2 引脚（Slot 1）。**

这意味着多麦克风配置下，物理通道顺序永远是：
- 1MIC+REF: `[Slot0=MIC, Slot1=REF]` → "MR" ✅（无需重排）
- 2MIC+REF: `[Slot0=MIC1, Slot1=REF, Slot2=MIC2]` → 需重排为 "MMR"
- 3MIC+REF: `[Slot0=MIC1, Slot1=REF, Slot2=MIC2, Slot3=MIC3]` → 需重排为 "MMMR"

---

## 五、AFE 单麦回退机制

`esp-sr` 的 AFE（Audio Front-End）对于 `AFE_TYPE_VC`（语音通信场景）：

- **不支持多麦克风 BSS/SE 算法**
- 即使 `input_format="MMR"` 且 `se_init=true`，内部 `afe_config_check()` 会覆盖为单麦模式
- 只使用 **通道 0** 作为麦克风输入

因此双麦混音必须在 codec 层（`Read()` 函数）完成，**在数据送入 AFE 之前**将两路麦克风叠加到通道 0。

---

## 六、最终数据流

```
硬件 TDM 读取:  [MIC1, REF, MIC2]   ← 每帧 3 个 int16 采样
                    ↓
通道重排:        [MIC1, MIC2, REF]    ← REF 移到末尾
                    ↓
软件混音:        [MIC1+MIC2, 0, REF]  ← 两路麦克风叠加到 ch0
                    ↓
重采样:          24kHz → 16kHz（多通道独立重采样）
                    ↓
AFE feed:        AFE 读取 ch0 作为麦克风，ch2 作为 AEC 参考
                    ↓
AFE fetch:       单通道降噪+回声消除后的语音
                    ↓
Opus 编码:       16kHz 单声道 → 发送到服务器
```

## 八、注意事项

1. **`.channel = 4` 不可更改**：ES7210 TDM 模式下硬件固定 4 通道，通过 `channel_mask` 选择实际读取的通道
2. **通道重排仅在 `input_reference_ && microphone_channels_ >= 2` 时生效**：单麦板子不受影响
3. **混音使用饱和加法**：`clamp(-32768, 32767)` 防止 int16 溢出
4. **如需修改为 3MIC+REF**：只需改 `microphone_channels=3`，通道重排和混音逻辑自动适配

## 一、目标

在 vibratalkie 板上增加 OV2640 传感器支持，通过 config.json 构建变体切换，默认仍使用 GC0308。

## 三、传感器切换方法

C++ 代码层（`ruio_camera.cc/h`、`Esp32Camera`）与具体传感器型号无关，`esp_cam_sensor` 框架通过 Kconfig 自动加载对应驱动。切换传感器只需使用不同的构建变体：

- **GC0308（默认）**：构建 `vibratalkie`
- **OV2640**：构建 `vibratalkie-ov2640`

切换时必须 **fullclean 后重新编译**。

---

## 四、OV2640 构建配置

```json
{
    "name": "vibratalkie-ov2640",
    "sdkconfig_append": [
        "CONFIG_CAMERA_OV2640=y",
        "CONFIG_CAMERA_OV2640_AUTO_DETECT_DVP_INTERFACE_SENSOR=y",
        "CONFIG_CAMERA_OV2640_DVP_YUV422_640X480_6FPS=y",
        "CONFIG_CAMERA_OV2640_DVP_IF_FORMAT_INDEX_DEFAULT=1",
        "CONFIG_CAMERA_SENSOR_SWAP_PIXEL_BYTE_ORDER=y"
    ]
}
```

关键项说明：
- `CONFIG_CAMERA_SENSOR_SWAP_PIXEL_BYTE_ORDER=y`：OV2640 默认 YUV422 字节序为 UYVY，需启用硬件字节交换使输出为 YUYV，否则 JPEG 编码器会将 U/V 与 Y 通道混淆，导致图像出现条纹干扰。GC0308 不需要此选项。

---

## 五、问题排查与修复

### 问题 1：图像条纹干扰

**现象**：OV2640 拍摄的图像有明显条纹，AI 识别返回"画面因条纹干扰模糊"。

**原因**：OV2640 YUV422 默认输出字节序为 UYVY（U 在偶数位置），而 `esp_jpeg_enc` 期望 YUYV（Y 在偶数位置），U/V 和 Y 通道错位。

**修复**：在 OV2640 构建变体中启用 `CONFIG_CAMERA_SENSOR_SWAP_PIXEL_BYTE_ORDER=y`，OV2640 的 `IMAGE_MODE` 寄存器 bit0 置 1，硬件端完成字节交换。

> GC0308 不需要此选项，因其默认输出就是 YUYV 字节序。

---

### 问题 2：相机关闭后系统崩溃重启

**现象**：`Esp32Camera::Explain()` 完成拍照上传后，`DisableCameraLDOs()` 关闭相机 LDO 后设备立即重启。

**根因**：`DisableCameraLDOs()` 同时关闭了 LDO2(bit2, 2.8V AVDD) 和 LDO3(bit3, 1.8V DVDD)。OV2640 的 SCCB(I2C) 引脚 (GPIO2/3) 与 ES8311、ES7210、AXP173 **共享同一条 I2C 总线**。当 LDO2 关闭导致 OV2640 完全失电后，其 IO pad 内部 ESD 保护二极管正向导通（$V_{bus} > V_{CC} + V_D$，即 $3.3V > 0V + 0.3V$），将 I2C 总线电压钳位到约 0.3V，使总线上所有设备通信失败，触发系统崩溃。

> GC0308 未出现此问题，因其 SCCB IO pad 在 PWDN+失电状态下呈高阻态，不会从 I2C 总线吸取寄生电流。

**修复**（`vibratalkie_board.cc`）：
```cpp
void DisableCameraLDOs() {
    uint8_t val = Axp173::ReadReg(0x12);
    val &= ~(1 << 3); // 只关闭LDO3(1.8V DVDD)，保持LDO2(2.8V AVDD)
    WriteReg(0x12, val);
}
```

仅关闭 LDO3(1.8V DVDD)，保留 LDO2(2.8V AVDD) 始终开启：
- 相机在 PWDN=HIGH + DVDD off 状态下功耗极低（微安级）
- AVDD 维持 2.8V，SCCB 引脚 ESD 二极管不导通，I2C 总线正常
- 恢复到系统启动时的初始电源状态 `REG12=0x07`

---

### 问题 3：PowerDown 后 DVP 残留操作

**修复**（`ruio_camera.cc`）：
```cpp
void PowerManagedCamera::PowerDown() {
    if (camera_) {
        camera_.reset();  // ~Esp32Camera: STREAMOFF → munmap → close → esp_video_deinit
        vTaskDelay(pdMS_TO_TICKS(50));  // 等待DVP控制器完全释放
    }
    if (pwdn_pin_ >= 0) {
        gpio_set_direction(pwdn_pin_, GPIO_MODE_OUTPUT);
        gpio_set_level(pwdn_pin_, 1);   // PWDN=HIGH 进入掉电模式
    }
    if (power_off_callback_) {
        vTaskDelay(pdMS_TO_TICKS(20));  // 确保PWDN状态稳定后再关闭LDO
        power_off_callback_();
    }
}
```

## 六、注意事项

1. **切换传感器需 fullclean**：GC0308 和 OV2640 使用不同的 Kconfig 选项，必须全量重编
2. **LDO2(2.8V) 必须保持开启**：因 I2C 总线共享，关闭会导致 OV2640 的 ESD 二极管钳位总线
3. **上电延时统一 300ms**：对 GC0308 和 OV2640 均安全，确保 LDO 电压稳定和传感器 PLL 锁定
4. **OV2640 帧率较低**：640×480 仅 6fps（GC0308 为 16fps），但 JPEG 压缩尺寸更小

## 四、动态猫眼表情（VibratalkieEyeDisplay）

### 功能特性

- **猫咪风格大圆眼** + 竖瞳 + 高光点
- **眨眼动画**：快速眨眼（100ms闭/150ms开）+ 猫咪信任慢眨眼（300ms/400ms），每 3-5 次快眨后穿插一次慢眨

- **23 种表情**：neutral, happy, laughing, sad, angry, surprised, thinking, sleepy, winking 等
- **高光跟随**：高光点跟随瞳孔移动（30% 比例），限制在眼球边界内
- **聊天文字浮层**：半透明背景叠在眼睛上方显示，3 秒后自动消失，不遮挡眼睛动画
- **字体自动升级**：启动时用 basic 字体，assets 加载后通过 SetTheme() 自动切换为 common 完整字体

采用项目标准的 **basic + common 二级字体方案**：

## 一、目标

实现像素级写实眼球渲染，替代 LVGL 矢量卡通眼睛。通过预生成的真实眼睛位图数据（巩膜 + 虹膜纹理 + 眼睑遮罩），在 SPI LCD 上以独占 DMA 方式逐批合成输出，帧率不受 LVGL 限制。

## 三、渲染架构（五层合成）

每帧按以下优先级逐像素合成，输出 RGB565 到 SPI DMA 缓冲：

```
第1层: 眼皮遮罩  → 像素灰度值 ≤ 阈值时显示黑色（眼皮闭合区域）
第2层: 巩膜      → 不在虹膜范围内时，查 sclera_data_[375×375] 得到白眼球颜色
第3层: 虹膜      → 在虹膜范围(150×150)内，查 polar_data_ 极坐标表得角度+半径，
                   再用 iScale 缩放半径查 iris_data_[471×75] 展开纹理
黑色背景         → 圆形屏幕边缘（眼皮完全遮挡）
```

**位图尺寸关系（240×240 屏）：**

| 位图 | 尺寸 | 说明 |
|------|------|------|
| 巩膜 (sclera) | 375×375 | 比屏幕大 135px，留出眼球移动空间 |
| 虹膜 (iris) | 150×150 | 眼球中央彩色区域 |
| 极坐标表 (polar) | 150×150 | 每像素16位：低7位=半径，高9位=角度 |
| 虹膜纹理 (iris_map) | 471×75 | 展开的虹膜花纹（宽=角度，高=半径） |
| 眼睑遮罩 (upper/lower) | 240×240 | 灰度值 0-255，值越小=越靠近眼皮边缘 |

**DMA 输出方式：** 每次处理 10 行（`EYE_LINES_PER_BATCH`），双缓冲交替，直接调用 `esp_lcd_panel_draw_bitmap`，完全绕过 LVGL 渲染链。

## 四、动画系统

### 眼球位置缓动

## 五、LVGL 隔离机制

`VibratalkieBitmapEyeDisplay` 继承自 `SpiLcdDisplay`，但完全绕过 LVGL：

```cpp
// 构造函数中替换两个回调：

// 1. LVGL flush 回调 → 空操作（阻止 LVGL 向 SPI 写数据）
lv_display_set_flush_cb(display_, dummy_flush_cb);

// 2. SPI 传输完成回调 → 空操作（阻止 draw_bitmap 触发 lv_display_flush_ready）
const esp_lcd_panel_io_callbacks_t io_cbs = { .on_color_trans_done = noop_color_trans_done };
esp_lcd_panel_io_register_event_callbacks(panel_io, &io_cbs, nullptr);
```

以下接口重写为空操作，外部调用不会触发 LVGL 渲染：
- `SetStatus()` / `ShowNotification()` / `SetTheme()` / `UpdateStatusBar()`

## 六、眼球任务死锁修复

### 问题现象

音频 Codec 初始化完成（`I2S` + `AudioService` 开始运行）后约 8-15 秒，眼球渲染画面冻结，`EyeLoopTask` 永久阻塞，串口不再刷新眼球相关日志。

### 根本原因

```
esp_lcd_panel_draw_bitmap()
  └─ panel_io_spi_tx_color()
       ├─ spi_device_acquire_bus(portMAX_DELAY)   ← 等待 SPI 总线空闲
       └─ spi_device_get_trans_result(portMAX_DELAY) ← 等待 DMA 完成中断
```

SPI DMA 完成回调需要在 **中断服务例程** 中触发，而该 ISR 绑定在 **Core 1**。音频 I2S 输出任务（优先级 10+，Core 1）启动后持续占满 Core 1，导致 SPI DMA 完成 ISR 无法被调度，`portMAX_DELAY` 等待永远不返回 → 死锁。

**涉及任务的 Core 分布（修复前）：**

| 任务 | Core | 优先级 |
|------|------|--------|
| eye_loop | Core 1 | 5 |
| LVGL | Core 1 | 1 |
| I2S 音频输出 | Core 1 | 10+ |
| SPI DMA ISR | Core 1 | - |

eye_loop 在 Core 1 上调用 `draw_bitmap` → 等待 DMA 完成 → ISR 需要 Core 1 运行 → Core 1 被音频任务占满 → **永久死锁**。

### 修复方案

```cpp
// 修复前
xTaskCreatePinnedToCore(EyeLoopTask, "eye_loop", 8192,  this, 5, &eye_task_, 1);

// 修复后：固定到 Core 0，物理隔离音频任务，提升优先级，扩展栈
eye_running_ = true;
xTaskCreatePinnedToCore(EyeLoopTask, "eye_loop", 12288, this, 8, &eye_task_, 0);
```

同时在 `DrawEye` 中每 4 批次让出 CPU，避免独占 Core 0 影响网络/系统任务：

```cpp
esp_lcd_panel_draw_bitmap(panel_, 0, screenY, SCREEN_WIDTH, screenY + linesToProcess, currentBuf);
if ((screenY & 0x28) == 0) taskYIELD();
```

**修复后任务分布：**

| 任务 | Core | 优先级 | 说明 |
|------|------|--------|------|
| eye_loop | **Core 0** | **8** | 物理隔离于音频 |
| LVGL | Core 1 | 1 | 不影响 SPI 总线 |
| I2S 音频输出 | Core 1 | 10+ | 独占 Core 1 |
| SPI DMA ISR | Core 1 | - | 无竞争，正常触发 |

## 七、eye_data_generator.py 眼睛数据生成工具更新

### 功能概述

Python GUI 工具，从真实眼睛照片自动生成 C 头文件（`sclera.h` / `iris.h` / `eyelid.h`），供 `VibratalkieBitmapEyeDisplay` 直接编译到固件。

### 新增功能

#### 1. 虹膜选区（双圆定位）

用户在源图上通过 4 个参数精确指定虹膜区域：

| 参数 | 说明 |
|------|------|
| X 偏移 | 虹膜中心相对于眼球中心的水平偏移（像素） |
| Y 偏移 | 虹膜中心相对于眼球中心的垂直偏移（像素） |
| 外径 | 虹膜外边界半径（包含虹膜完整范围） |
| 内径 | 瞳孔内边界半径（极坐标展开时的采样起点） |

预览画布叠加两个黄色圆圈（`#ffd400`）实时显示选区：
- **外圆**（实线）：虹膜/巩膜分界线
- **内圆**（实线）：瞳孔边界，极坐标展开从此处开始采样

极坐标展开时，采样半径范围为 `[inner_r_in_crop, max_r]`，避免将纯黑瞳孔区域映射到虹膜纹理。

#### 2. 巩膜中心叠加图

巩膜生成时中心虹膜区域保留黑色空洞，同时支持可选叠加图片覆盖该区域：

```
黑色空洞区域  ← iris_mask（dist < iris_r 的像素全部置 0）
      +
叠加图片（可选）← 若指定，将其 resize 到瞳孔直径后粘贴到黑色区域内
```

GUI 提供文件选择按钮，修改路径后自动触发预览刷新。

#### 3. UI 布局优化

- 所有控件行间距从 5px 压缩到 2px
- 预览画布高度 260→220px
- 描述文字改为单行显示，合并虹膜/眼皮提示文字
- 节省约 100px 垂直高度，适配小屏幕显示器
